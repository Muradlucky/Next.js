# Блок 3. ECC 2.0 и контроль качества работы агентов

Учебный разбор проекта everything-claude-code (ECC), автор Affaan Mustafa, лицензия MIT. Версия исходников: `affaan-m/everything-claude-code @ 25278e7 (2.2.3)`. Все пути ниже даны от корня репозитория. Код я только читал, ничего не запускал и не собирал.

Краткая суть для владельца агентства:

- **ECC 2.0** — программа-«диспетчер» для одновременной работы многих агентов. Её запускают на своём компьютере в терминале. Это ранняя тестовая версия (альфа). При облачной схеме без своего компьютера ставить её незачем, но несколько её идей можно перенести один к одному.
- **Контроль качества** в ECC — набор приёмов: рубрика оценки, повторные прогоны, два независимых проверяющих, связка «исполнитель — строгий критик», «ворота» перед выдачей результата. Почти всё это переносится в облачную схему без установки, потому что это способы организовать работу, а не программы.

## Часть 1. ECC 2.0

### 1.1. Что это простыми словами

ECC 1.x — это набор текстовых инструкций (агенты, навыки, команды) и маленьких скриптов-«хуков» внутри одной сессии Claude Code. ECC 2.0 — уровень выше: отдельная программа на языке Rust. Она **запускает много сессий агентов параллельно, следит за ними и показывает всё на одном экране**. Сам автор называет её «пультом управления» (control plane):

> `ECC 2.0 is the layer above individual harness installs.` … `manage many agent sessions from one surface` — `ecc2/README.md`
> (ECC 2.0 стоит над отдельными установками агентов… цель — управлять многими сессиями из одного места.)

«Harness» (дословно «упряжь», здесь «обвязка») — программа, внутри которой работает модель: Claude Code, Codex, Gemini CLI и т. п. ECC 2.0 умеет запускать несколько видов обвязок, но в первую очередь Claude Code.

### 1.2. Из каких частей состоит

```
            Вы (оператор) в терминале
                     │
     ┌───────────────┴────────────────┐
     │  CLI-команды    │  TUI-панель   │  tui/  (экран в терминале:
     │  start, delegate│  Sessions,    │   сессии, вывод, метрики,
     │  assign, stop…  │  Output, Board│   доска, журнал)
     └───────┬─────────┴──────┬────────┘
             │                │
     ┌───────▼────────────────▼────────┐
     │  session/manager  — запуск и    │──► claude --print --name ecc-<id>
     │  остановка агентов, делегирование│    (отдельный процесс на сессию)
     └───────┬─────────────────────────┘
             │            ┌──────────────────────┐
             ├───────────►│ worktree/ — у каждой  │  отдельная рабочая копия
             │            │ сессии своя копия кода│  репозитория (git worktree)
             │            └──────────────────────┘
     ┌───────▼─────────────────────────┐
     │  session/store — SQLite-база     │ ~/.claude/ecc2.db: сессии, журнал
     │  (единый источник правды)        │ инструментов, сообщения, расписание,
     └───────▲───────────▲─────────────┘ конфликты, решения
             │           │
   ┌─────────┴──┐  ┌─────┴──────────────────┐
   │ daemon     │  │ observability          │ ◄── хук пишет каждое действие
   │ фоновый    │  │ журнал действий +      │     агента в tool-usage.jsonl
   │ цикл 30 с  │  │ оценка риска           │
   └─────┬──────┘  └────────────────────────┘
         │
   comms (сообщения между сессиями) · notifications (рабочий стол, Slack, Discord)
   harness_eval (сравнение версий настроек перед «повышением»)
```

Что делает каждая часть (папка `ecc2/src/`):

| Часть | Что делает |
|---|---|
| `main.rs` | Командная строка. Команды: `start`, `delegate` (поручить подзадачу от одной сессии другой), `assign` (отдать работу свободному исполнителю или создать нового), `template` (запустить именованный сценарий из конфига), `auto-dispatch`, `daemon`, `dashboard`, `remote serve` и др. |
| `session/` | Модель сессии и её состояния: `Pending, Running, Idle, Stale, Completed, Failed, Stopped`. Здесь же запуск агента. |
| `session/store.rs` | База SQLite: таблицы `sessions`, `tool_log`, `messages`, `session_board`, `decision_log`, `scheduled_tasks`, `conflict_incidents`, `daemon_activity`, `harness_*` и др. |
| `session/daemon.rs` | Фоновый процесс (демон), который работает по кругу. |
| `worktree/` | Отдельные рабочие копии кода, проверка готовности к слиянию, предпросмотр конфликтов, черновой PR. |
| `comms/` | Типы сообщений между агентами. |
| `observability/` | Журнал действий и оценка риска (risk scoring). |
| `notifications.rs` | Уведомления на рабочий стол и вебхуки в Slack или Discord. |
| `config/` | Файл настроек `ecc2.toml`: профили агентов, лимиты, пороги риска. |
| `tui/` | Экранная панель в терминале (библиотека ratatui). |
| `harness_eval.rs` | «Ворота повышения»: новую версию настроек сравнивают со старой. |

Отдельно лежит `ecc_dashboard.py`. К управлению сессиями он **не относится**: это настольное окно на Python и Tkinter, которое показывает каталог агентов, навыков и команд ECC с поиском. Нужен рабочий стол с графикой.

### 1.3. Как это работает по шагам

1. **Запуск сессии.** Команда `start --task "…" --agent claude --worktree` создаёт запись в базе (`Pending`). Если включено, она же делает отдельную рабочую копию кода. Затем запускается процесс агента. Для Claude это буквально:

   > `.arg("--print").arg("--name").arg(format!("ecc-{session_id}"))` — `ecc2/src/session/manager.rs`

   Из «профиля» в `ecc2.toml` подставляются модель, разрешённые и запрещённые инструменты, режим разрешений, бюджет в долларах (`--max-budget-usd`) и добавка к системному промпту. Получается та же схема, что у вас: «роль = набор ограничений + инструкция».
2. **Изоляция через worktree.** Git worktree — вторая (третья, …) рабочая папка того же репозитория на своей ветке. Каждый агент правит свою копию и не мешает соседям. Потом изменения проверяют на конфликты и сливают. По умолчанию копии лежат в `/tmp/ecc-worktrees`, одновременно не больше 6 копий и 8 сессий.
3. **Наблюдение.** Хук `scripts/hooks/session-activity-tracker.js` после каждого действия агента дописывает строку в `~/.claude/metrics/tool-usage.jsonl`, предварительно вычищая токены и пароли. ECC 2.0 переносит эти строки в базу, и каждому действию присваивается оценка риска.
4. **Общение агентов.** Сообщения хранятся в таблице `messages` и бывают строго определённых типов:

   > `TaskHandoff { task, context, priority }` · `Query { question }` · `Response { answer }` · `Completed { summary, files_changed }` · `Conflict { file, description }` — `ecc2/src/comms/mod.rs`

   То есть: передача задачи (что сделать, контекст, приоритет), вопрос, ответ, отчёт о завершении (итог и список изменённых файлов), сигнал о конфликте.
5. **Демон.** Каждые 30 секунд (`heartbeat_interval_secs: 30`) он делает круг:

   > `check_sessions` → `maybe_run_due_schedules` → `maybe_run_remote_dispatch` → `coordinate_backlog_cycle` → `maybe_auto_merge_ready_worktrees` → `maybe_auto_prune_inactive_worktrees` — `ecc2/src/session/daemon.rs`

   По шагам: проверить «пульс» сессий (зависшие помечаются `Stale`), запустить задачи по расписанию, принять внешние заявки, раздать накопившиеся поручения и перераспределить очередь, при желании автоматически слить готовые копии (по умолчанию выключено), убрать неактивные копии. При старте демон ищет сессии со статусом `Running`, чей процесс уже умер, и помечает их `Failed`.
6. **Панель.** `dashboard` показывает экран из пяти областей: сессии, вывод, метрики, доска, журнал. Данные берутся из той же базы.

### 1.4. Что такое risk scoring

Каждое действие агента получает число от 0 до 1. Это **сумма четырёх простых признаков**, найденных по ключевым словам (`ecc2/src/observability/mod.rs`):

| Признак | Пример | Добавка |
|---|---|---|
| Тип инструмента | Bash 0.20, Write 0.15, Edit 0.10, прочие 0.05 | 0.05–0.20 |
| Чувствительность цели | `.env`, `token`, `id_rsa` → 0.25; `package.json`, `migration`, `production` → 0.15 | 0–0.25 |
| Радиус поражения | `git push --force`, `origin main`, `rm -rf /` → 0.35; `**`, `--recursive`, `all files` → 0.25 | 0–0.35 |
| Необратимость | `rm -rf`, `git reset --hard`, `drop table` → 0.45; `rm -f`, `delete from` → 0.40 | 0–0.45 |

Пороги (`ecc2/src/config/mod.rs`): `review: 0.35, confirm: 0.60, block: 0.85`. Ниже 0.35 — «разрешить», от 0.35 — «посмотреть», от 0.60 — «требовать подтверждения», от 0.85 — «заблокировать». Примеры:

- правка README: 0.10, разрешено;
- правка `.env`: 0.10 + 0.25 = 0.35, на просмотр;
- `git push --force origin main`: 0.20 + 0.35 + 0.40 = 0.95, блок.

Сильная сторона — объяснимость: к оценке прилагаются причины (`reasons`). Слабая — это поиск по словам. Его легко обойти, и он не понимает смысла команды.

### 1.5. Где хранится состояние

Всё хранится в одном файле SQLite (`~/.claude/ecc2.db`). README подчёркивает, что база — «источник правды» для всех процессов:

> `the database remains the cross-process source of truth` — `ecc2/README.md`

У вас ту же роль играет общий статус-документ в Google Docs. Разница в том, что база хранит строки с жёсткими полями (статус, время пульса, ID), а не свободный текст.

### 1.6. Статус готовности

Сам автор пишет прямо:

> `It is usable as an alpha for local experimentation, but it is **not** the finished ECC 2.0 product yet.` … `Do not market ecc2/ as done just because the scaffold builds.` — `ecc2/README.md`
> (Можно пробовать локально как альфу, но это не готовый продукт. Не рекламировать как готовое только потому, что каркас собирается.)

**Уже есть:** терминальная панель, база сессий, запуск, остановка и возобновление, демон, оценка риска, worktree, отслеживание вывода, сообщения, расписание, «ворота» сравнения настроек. Версия пакета — `0.1.0`.

**Пока нет** (по списку в README): развитая оркестрация многих агентов, явное делегирование со сводками, визуальный просмотр изменений, совместимость с другими обвязками, глубокая память и планирование, установщик.

Документ `docs/control-plane/VIEW-CONTRACT.md` описывает уже выпущенный «живой вид». Это JSON, в котором сессии разложены по задачам, дорожкам и событиям. Он только читает данные и только советует. `docs/control-plane/TCAS-HOOK.md` помечен как `design only. Nothing in this document is implemented`: это проект хука, который не даёт двум агентам править один файл. Название взято у авиационной системы TCAS, которая разводит самолёты: один «держит курс», другой «отворачивает». В `docs/ECC-2.0-GA-ROADMAP.md` план расписан по «полосам», каждая — с жёсткими требованиями к тестам. Среди них: сначала доступ «только на чтение», потом изменения; аренда файлов; телеметрия только с согласия. Даты этапов там целевые, а выполнены ли они, по исходникам проверить нельзя.

### 1.7. На чём работает

- **Локально.** Нужен компьютер (Linux, macOS или Windows), Rust и `cargo` для сборки, git, установленный и авторизованный `claude` CLI и терминал для панели. tmux самой программе не нужен: в коде он не встречается. Он нужен соседним приёмам ECC (`dmux-workflows`) и упоминается среди образцов в `ECC-2.0-REFERENCE-ARCHITECTURE.md`.
- Сервер приёма заявок (`remote serve`) по умолчанию слушает только `127.0.0.1:8787`, то есть сам компьютер, и требует токен.
- Каждая запущенная сессия — отдельный расход на API.

**Можно ли использовать в облачной схеме?** Технически облачный контейнер — тоже Linux, и собрать программу там можно. Но практического смысла нет:

1. Контейнер временный: демон и база исчезнут вместе с сессией.
2. Терминальную панель вам смотреть негде.
3. Почти всё, что даёт ECC 2.0, у вас уже даёт облачная платформа. Дочерние сессии заменяют `start` и `delegate`, сообщения между сессиями — таблицу `messages`, задачи по расписанию — `scheduled_tasks` и демон, статус сессии (`working / blocked / failed…`) — `SessionState`. Изоляцию даёт отдельный контейнер на каждую дочернюю сессию вместо worktree.
4. Это альфа.

**Вывод: не ставить, а перенять идеи.**

### 1.8. Похоже и отличается

| | ECC 2.0 | Ваш облачный оркестратор |
|---|---|---|
| Где живёт | Ваш компьютер, терминал | Облако, браузер или приложение |
| Исполнители | Процессы `claude --print` | Дочерние облачные сессии |
| Изоляция | git worktree (папка) | Отдельный контейнер |
| Общее состояние | SQLite, жёсткие поля | Google Docs, свободный текст |
| Сообщения | 5 типизированных видов | Свободный текст между сессиями |
| Расписание | Демон каждые 30 с | Задачи по расписанию платформы |
| Риски | Автоматическая оценка каждого действия | Режим разрешений сессии и ваши инструкции |
| Зависание | Пульс → `Stale` | Нужно проверять статус вручную или по расписанию |

### 1.9. Что перенять без установки

1. **Жёсткие поля в статусе.** Завести в статус-документе таблицу: ID задачи, роль, состояние (из 7 слов, как в ECC), время последнего обновления, ссылка на результат.
2. **Типы сообщений.** Передавать задачу по шаблону «задача / контекст / приоритет», а отчитываться по шаблону «итог / что изменено (ссылки на документы)». Вопросы и конфликты — отдельными видами сообщений.
3. **Пульс и «зависание».** Если дочерняя сессия не обновляла свою строку дольше N минут, оркестратор помечает её «зависла» и разбирается.
4. **Шкала риска действий** (подробнее в части 3).
5. **«Ворота повышения» для инструкций** из `harness_eval`. Новая версия настроек становится активной, только если на тех же тестах она лучше старой: заданы минимальное число пар, минимальный средний прирост и доля побед. Каждое решение пишется в неизменяемый журнал, при сбое возвращается прежняя версия. Автор честно оговаривает ограничения: оценки вводит человек, и это не статистическая значимость.
6. **Правило «права дороги»** из TCAS. Если два агента должны править один документ, правит тот, кто дальше продвинулся, а второй ждёт или переходит к другой части.

## Часть 2. Контроль качества

### 2.1. Пятиосевая рубрика (agent-evaluator + agent-self-evaluation)

**Что это.** Отдельный агент-оценщик (`agents/agent-evaluator.md`) ставит результату работы другого агента оценки от 1 до 5 по пяти осям. Сам задачу он не переделывает:

> `Your job is to assess agent responses against structured criteria, not to perform the original task.` … `Every score below 5 MUST cite specific evidence from the output` — `agents/agent-evaluator.md`
> (Ваша задача — оценить, а не выполнить задачу заново. Любая оценка ниже 5 обязана ссылаться на конкретное место в результате.)

**Как устроено.** 1) Прочитать исходный запрос и результат. 2) Проверить утверждения инструментами: существуют ли файлы, проходят ли тесты. 3) Оценить каждую ось отдельно. 4) Выдать отчёт с вердиктом. У оценщика есть Bash, но разрешены только читающие команды (`grep`, `cat`, `ls`…).

**Рубрика полностью** (перевод `skills/agent-self-evaluation/SKILL.md` и `references/evaluation-criteria.md`):

| Ось | Вопрос | Что ловит |
|---|---|---|
| Точность | Верны ли факты, утверждения, результат? | Выдумки, неверные названия, ложные утверждения |
| Полнота | Покрыто ли всё, о чём просили? | Пропущенные случаи, забытые требования и подзадачи |
| Ясность | Понятно и хорошо ли структурировано? | Путаные объяснения, термины без пояснений, «вода» |
| Применимость | Можно ли сразу действовать по результату? | Расплывчатые советы, недостающие шаги, нет способа проверить |
| Краткость | Минимум слов для задачи? | Повторы, переобъяснение, пересказ вопроса, наполнитель |

Шкала: **5** — исключительно, улучшать нечего; **4** — хорошо, только мелочи; **3** — приемлемо, но есть заметная слабость; **2** — слабо, пробел мешает пользоваться или делает результат неверным; **1** — плохо, мимо запроса или серьёзные ошибки.

Правило доказательств: «Покажи пробел, а не просто назови его». Тройка не может звучать как «можно лучше», она должна указать, что именно не так.

Ориентиры по баллам:

- **Точность.** 5 — всё сверено с инструментами или документами. 4 — одна мелкая неточность, на правильность не влияет. 3 — одна серьёзная ошибка или 3+ мелких. 2 — несколько серьёзных, по инструкции ничего не заработает. 1 — в корне неверно, противоречит само себе. *Особый случай: заявлено «тесты прошли», а вывод показывает провал — автоматически ≤ 2.*
- **Полнота.** 5 — все явные и подразумеваемые требования и пограничные случаи. 4 — все явные, пропущено одно подразумеваемое. 3 — пропущено одно явное или 2+ подразумеваемых. 2 — пропущено несколько явных, решение частичное. 1 — сделано «что-то рядом» вместо запрошенного.
- **Ясность.** 5 — идеальная структура, без двусмысленностей. 4 — один раздел или термин можно лучше. 3 — понятно со второго прочтения. 2 — местами путано, будут вопросы. 1 — непонятно или противоречиво.
- **Применимость.** 5 — одно действие и путь проверки. 4 — одно действие, но проверка подразумевается. 3 — несколько действий или неясен следующий шаг. 2 — пользователю самому собирать результат. 1 — без серьёзной доработки действовать нельзя.
- **Краткость.** 5 — каждое предложение на месте. 4 — один абзац можно ужать. 3 — 20%+ можно убрать без потерь. 2 — 40%+ наполнитель. 1 — шума больше, чем сути.

Пограничные случаи: если запрос был неясен, за «нечтение мыслей» не наказывают, а называют выбранное толкование. Простая задача, сделанная идеально, честно получает 5.0. Если агент сам нашёл и исправил ошибку до сдачи, это не штраф.

Формат отчёта: итог одной строкой → пять осей (балл, «+» доказательства, «→» улучшение) → средний балл → **критические проблемы (оси ≤ 2)** → самопроверка «согласился бы пользователь с этой оценкой?» → 1–3 главных улучшения → **вердикт: «сдавать как есть» / «исправить N пунктов и сдать» / «переделать»**.

Анти-паттерны из навыка: «всё на пятёрку» без доказательств; штраф за то, о чём не просили; оценка как повод снова спорить о решении; вкусовщина («мне не нравится») вместо довода.

**Сильные стороны.** Понятно, переносится на любой текст, а не только на код, и требует доказательств. **Ограничения.** Скрипт `scripts/evaluate.py` при навыке — это эвристики по ключевым словам. Автор сам пишет: `For production use, pair with an LLM judge` (для реальной работы нужен оценщик-модель). Кроме того, режим *само*оценки слаб: соседний навык GateGuard прямо утверждает `LLM self-evaluation doesn't work`. Вывод: рубрику стоит отдавать **отдельному** агенту.

### 2.2. pass@k и pass^k простыми словами

Агент недетерминирован: одна и та же задача то получается, то нет. Поэтому её прогоняют k раз (`skills/eval-harness/SKILL.md`):

- **pass@k** — «хотя бы одна удача из k попыток». Подходит, когда человек выбирает лучший из трёх черновиков.
- **pass^k** — «все k попыток удачны». Подходит, когда агент работает без присмотра по расписанию.

Пример: агент справляется в 70% случаев. Тогда pass@3 = 1 − 0,3³ ≈ **97%**, а pass^3 = 0,7³ ≈ **34%**. Один и тот же агент выглядит отлично по первой мере и ненадёжно по второй. ECC рекомендует:

> `Capability evals: pass@3 >= 0.90` · `Regression evals: pass^3 = 1.00 for release-critical paths` — `skills/eval-harness/SKILL.md`

Здесь capability eval — проверка «умеет ли новое», а regression eval — «не сломалось ли старое». Проверяющие (graders) бывают четырёх видов: кодом (детерминированно), правилом (шаблон или схема), моделью (LLM-судья по рубрике) и человеком. Совет: `Use code graders when possible - Deterministic > probabilistic` (где можно, проверять кодом). Анти-паттерны: подгонка промптов под известные тесты, проверка только «счастливого пути», «плавающий» проверяющий в воротах выпуска.

Родственный навык `agent-eval` делает то же для сравнения агентов между собой: задачи в YAML, минимум 3 прогона, метрики «доля успехов, цена, время, стабильность». Совет оттуда: в каждой задаче хотя бы один детерминированный судья, потому что LLM-судья добавляет шум.

### 2.3. Санта-метод (два независимых проверяющих)

**Что это.** «Составь список, проверь дважды». Один агент делает, двое проверяют по одной рубрике и не видят мнений друг друга. Результат выходит, только если **оба** сказали PASS. Ключевая мысль:

> `a single agent reviewing its own output shares the same biases, knowledge gaps, and systematic errors that produced the output.` — `skills/santa-method/SKILL.md`
> (Агент, проверяющий свою работу, разделяет те же слепые пятна, которые эти ошибки породили.)

**По шагам.**

1. Генератор делает работу как обычно.
2. Два проверяющих запускаются параллельно с одинаковыми входными данными (задание + результат + рубрика) и возвращают структурированный вердикт: `verdict`, `checks`, `critical_issues`, `suggestions`.
3. Ворота: оба PASS — «NICE», выпускаем. Иначе «NAUGHTY»: замечания объединяются.
4. Исправляются **только** отмеченные проблемы. Затем проверка повторяется **новыми** проверяющими без памяти о прошлом круге, чтобы предыдущие выводы не задавали рамку.
5. Максимум 3 круга, дальше вопрос передаётся человеку.

> `Why both must pass: if only one reviewer catches an issue, that issue is real.` — `skills/santa-method/SKILL.md`

Команда `commands/santa-loop.md` — версия для кода. Второй проверяющий по возможности берётся **другой моделью** (Codex или Gemini), потому что разнообразие моделей снижает общие слепые пятна. Отказ внешнего проверяющего не считается одобрением. Публикация (`git push`) происходит только после NICE.

Для больших пачек есть выборочная проверка: 10–15% пачки, но не меньше 5 штук. Найденный системный дефект исправляют во всей пачке и снова делают выборку.

**Сильные стороны.** Ломает «самоодобрение», рубрика с объективными критериями PASS/FAIL, есть предохранитель от бесконечного цикла. Предлагаемые метрики: доля прохождения с первого раза (цель > 70%), согласие проверяющих (низкое согласие — сигнал, что рубрика размыта), «утечки» после выпуска (цель 0). **Ограничения.** Стоит в 2–3 раза дороже генерации. Если оба проверяющих одной модели, они могут промахнуться одинаково. Автор пишет, что независимость это смягчает, но не устраняет, и для критичного советует третьего проверяющего или человека.

### 2.4. GAN-подход (генератор против оценщика)

**Что это.** Подход назван по аналогии с GAN из машинного обучения: одна сеть создаёт, другая ищет подделку. Навык `skills/gan-style-harness/SKILL.md` ссылается на инженерную статью Anthropic о многочасовых задачах. В нём три агента: **планировщик** (`agents/gan-planner.md`) разворачивает одну строку в подробное задание и сразу пишет рубрику для оценщика; **генератор** (`agents/gan-generator.md`) делает; **оценщик** (`agents/gan-evaluator.md`) проверяет **живой результат** (кликает по приложению в браузере), а не только читает код.

> `agents are pathological optimists — they praise mediocre output` … `engineering a separate evaluator to be ruthlessly strict is far more tractable than teaching a generator to self-critique.` — `skills/gan-style-harness/SKILL.md`
> (Агенты — патологические оптимисты. Сделать отдельного беспощадного оценщика гораздо проще, чем научить исполнителя самокритике.)

**По шагам.** Планировщик пишет `spec.md` и `eval-rubric.md`. Генератор делает первую итерацию. Оценщик ставит баллы 1–10 по взвешенным критериям (дизайн 0.3, оригинальность 0.2, мастерство 0.3, функциональность 0.2) и пишет `feedback-NNN.md`. Генератор читает **файл** с отзывом и улучшает. Цикл длится до порога 7.0 или до 15 итераций.

Важные правила: отзыв передаётся файлом, а не на словах. Оценщик только критикует и никогда не чинит сам, иначе он начнёт хвалить свои исправления. Если три итерации подряд прироста нет, работа останавливается и передаётся человеку. Если инструментов браузера нет, оценщик обязан честно сообщить о «понижении режима».

**Сильные стороны.** Качество делает скачок. **Ограничения.** Это очень дорого: по приведённой таблице примерно в 20 раз дороже и дольше одиночного агента. Подход рассчитан на большие задачи. И ещё мысль, полезная для обучения: `Every harness component encodes an assumption about what the model can't do alone` (каждая деталь обвязки — предположение о слабости модели). Когда модели становятся сильнее, лишние детали надо снимать.

### 2.5. «Ворота» перед выдачей результата

В ECC несколько разных «ворот». Важно не путать, что каждые из них проверяют на самом деле.

| Ворота | Когда срабатывают | Что проверяют | Блокируют? |
|---|---|---|---|
| `verification-loop` | По команде, перед сдачей | 6 фаз: сборка, типы, линтер, тесты с покрытием ≥ 80%, поиск секретов, просмотр изменений → «READY / NOT READY» | Как инструкция |
| `quality-gate` | После каждой правки файла (хук) | **Только форматирование** одного файла | Нет (кроме строгого режима) |
| `delivery-gate` | Когда агент хочет закончить (хук Stop) | Механические факты: свободное место на диске, обновлялись ли сегодня журналы обучения, фразы-оправдания вроде «пропустим тесты пока» | Да, при нехватке диска или забытых журналах на сложной задаче |
| `gateguard` | Перед первой правкой каждого файла (хук PreToolUse) | Требует сначала предъявить факты | Да, первая попытка отклоняется |

Название `quality-gate` обманчиво: в описании прямо сказано `Lint and type checks are not part of this gate`.

`delivery-gate` устроен мудро: `using only deterministic checks … No AI inference` (только детерминированные проверки, без участия модели). Предупреждения о фразах-оправданиях никогда не блокируют сами, потому что поиск по шаблону даёт ложные срабатывания. Есть и защита от бесконечного цикла: один и тот же Stop блокируется максимум один раз. Ограничение автор называет сам: хук проверяет **привычку** обновлять журнал, а не **качество** записи.

**GateGuard** работает в три шага: отказать — потребовать факты — разрешить повтор.

> `Ask "did you violate any policies?" and the answer is always "no."` … `But asking "list every file that imports this module" forces the LLM to run Grep and Read.` — `skills/gateguard/SKILL.md`
> (На вопрос «ты нарушил правила?» ответ всегда «нет». А просьба перечислить, кто зависит от файла, заставляет реально пойти и посмотреть.)

Перед правкой агент должен перечислить, кто использует файл, что затрагивает изменение и какой формат данных, а также **дословно процитировать текущее указание пользователя**. Перед опасной командой нужны три вещи: что будет изменено или удалено, однострочный план отката и цитата указания. Заявленный эффект — +2,25 балла по 10-балльной шкале, но это всего **две** задачи в A/B-тесте. Это иллюстрация, а не доказательство.

Ещё два навыка про проверку проверок:

- `skill-comply` измеряет, **соблюдают ли агенты** инструкции на деле. Для каждого правила он генерирует сценарии трёх уровней: промпт поддерживает правило, нейтрален или подталкивает его нарушить. Затем по журналу действий проверяет, выполнены ли шаги и в правильном ли порядке.
- `ai-regression-testing`: `AI writes fix → AI reviews fix → AI says "looks correct" → Bug still exists`. Его рецепт — тест пишется там, где уже нашли ошибку, и называется по этой ошибке («BUG-R1 regression»). Цель — не процент покрытия, а невозможность повторения.

### 2.6. Защита от опасных действий

Механизмов три, и сила у них разная:

1. **`safety-guard`** — три режима. «Осторожный»: перед `rm -rf`, `git push --force`, `DROP TABLE`, `npm publish` спросить подтверждение. «Заморозка»: писать только в одну папку. «Охрана»: оба режима сразу. Главный урок — честная оговорка автора:

   > `This skill is advisory. ECC ships no /safety-guard command and no hook for it, so nothing blocks a tool call that breaks these rules.` — `skills/safety-guard/SKILL.md`
   > (Навык носит рекомендательный характер: ничто не помешает агенту его нарушить. Для настоящей блокировки нужны запрещающие правила разрешений или хук PreToolUse.)

2. **Хуки** (GateGuard, TCAS в проекте) реально останавливают действие, потому что их выполняет сама программа, а не модель.
3. **Оценка риска в ECC 2.0** (п. 1.4) — числовая шкала «разрешить / посмотреть / подтвердить / заблокировать».

Общая мысль: **инструкция — это просьба, настройка разрешений — это замок**.

## Часть 3. Что взять себе

Ниже — как встроить всё это в схему «облачный оркестратор + дочерние сессии + Google Docs». Ничего устанавливать не нужно.

**1. Документ «Рубрика качества» в Google Docs.** Взять пять осей из п. 2.1, переписать ориентиры под агентство (например, «Точность: все цифры и названия клиента сверены с исходными материалами») и добавить отраслевые пункты из санта-метода: тон бренда, обязательные оговорки, отсутствие обещаний результата. Каждый критерий должен иметь объективное «прошёл / не прошёл». Рубрика версионируется: v1, v2… с датой и причиной правки.

**2. Роль «Проверяющий» — отдельная дочерняя сессия.** В инструкции роли: только читать, не переделывать задачу, оценка ниже 5 только со ссылкой на конкретное место, вердикт из трёх вариантов. Исполнитель и проверяющий — **разные** сессии. Проверяющий никогда не исправляет сам: исправляет исполнитель по файлу-отзыву (правило GAN).

**3. «Санта-лайт» для всего, что уходит клиенту.** Оркестратор запускает двух проверяющих параллельно с одинаковыми входными данными (задание + результат + ссылка на рубрику) и ничего не говорит им друг о друге. Оба PASS — результат уходит на ваше утверждение или клиенту. Иначе исполнитель исправляет только отмеченное, проверку повторяют новые проверяющие. После 3 кругов вопрос переходит к вам. Для пачек (например, 40 постов) проверять выборку 15%, но не меньше 5. Для внутренних черновиков хватит одного проверяющего.

**4. Синтетические тесты → набор регрессии.** Ваши «правки по итогам синтетического теста» — готовые regression evals. Оформлять каждую карточкой: задача, критерии PASS/FAIL, вид проверяющего (правило, модель или вы), название по дефекту («ТЕСТ-07: путает сроки в брифе»). Прогонять каждый тест 3 раза и записывать два числа: pass@3 (умеет ли вообще) и pass^3 (надёжно ли). Для ролей, работающих по расписанию без присмотра, смотреть на pass^3.

**5. «Ворота повышения» для инструкций ролей** (идея `harness_eval`). Новая версия инструкции становится рабочей, только если на **тех же** тестах она не хуже старой ни на одном регрессионном тесте и в среднем лучше. Решение записывается в журнал (дата, версии, результаты), старая версия остаётся для отката.

**6. Проверка соблюдения** (идея `skill-comply`). Для важного правила роли сделать три варианта одного теста: просьба помогает правилу, нейтральна или подталкивает нарушить его («сделай быстро, без согласования»). Правило, которое держится только в первом случае, — слабое.

**7. Шкала риска действий агентства** — в инструкциях и в «Общем статусе»:

| Уровень | Примеры | Что делать |
|---|---|---|
| Разрешить | Черновик в своей папке, исследование | Сразу |
| Посмотреть | Правка общего статус-документа, инструкций ролей | Отметить в журнале, проверяющий смотрит |
| Подтвердить | Письмо клиенту, публикация, расход денег | Только после вашего «да» |
| Блокировать | Удаление файлов на Drive, смена доступа к документам | Никогда без вас |

Помните урок `safety-guard`: таблица в инструкции — это просьба. «Замок» — это режим разрешений и набор подключений, которые оркестратор выдаёт дочерней сессии при создании. Например, проверяющему не давать подключение к почте вообще.

**8. «Ворота» перед словом «готово»** (идея `delivery-gate`). Дочерняя сессия считается завершённой, только если выполнены механически проверяемые условия: обновлена её строка в статусе, есть ссылка на результат, есть вердикт проверяющего. Оркестратор проверяет факты (время изменения документа, наличие ссылки), а не верит отчёту «всё сделано».

**9. Факты до правки** (идея GateGuard). Прежде чем менять общий документ, агент пишет: какие роли опираются на этот документ, что именно меняется, и цитирует ваше указание дословно.

**10. Структура статус-документа** (идеи из ECC 2.0). Строки с жёсткими полями (ID, роль, состояние, время последнего обновления), типизированные сообщения «задача / контекст / приоритет» и «итог / что изменено», правило «зависла, если нет обновления N минут», правило «права дороги» для одного документа.

**Порядок внедрения:** сначала рубрика (1) и проверяющая роль (2), затем тесты с pass@3 / pass^3 (4), потом санта-лайт для клиентских материалов (3) и ворота повышения (5). Остальное — по мере роста.

## Часть 4. Вопросы для самопроверки и что изучить дальше

**Вопросы.**

1. Агент справляется с задачей в 80% случаев. Чему примерно равны pass@3 и pass^3? Какая из мер важна для роли, работающей ночью по расписанию? *(≈99% и ≈51%; вторая.)*
2. Почему в санта-методе каждый круг проверки делают **новые** проверяющие?
3. Почему GAN-оценщику запрещено самому исправлять найденное?
4. Чем «рекомендательный» навык отличается от хука или настройки разрешений? Приведите пример из своей схемы.
5. Какую оценку по точности получит отчёт «тесты прошли», если в выводе видна ошибка?
6. Какие три признака, кроме типа инструмента, складываются в оценку риска ECC 2.0? Почему поиск по словам — слабое место?
