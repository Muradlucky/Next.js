# Блок 01. Оркестрация и «совет» (council) в everything-claude-code

Разбор открытого проекта ECC (автор Affaan Mustafa, лицензия MIT), версия 2.2.3. Смотрим, как в нём устроены оркестрация агентов и спор по неоднозначному решению. Описано то, что реально лежит в файлах, а не то, что обещает README. Пути указаны от корня репозитория.

Термины, которые встретятся дальше:
- **Навык (skill)** — markdown-файл с инструкцией. Модель подгружает его, когда задача подходит под описание.
- **Агент (agent)** — markdown-файл с ролью и списком разрешённых инструментов. Его запускают как отдельного «субагента» с чистым контекстом.
- **Команда (command)** — slash-команда вида `/plan`, по сути тонкая обёртка над навыком.
- **Хук (hook)** — скрипт, который сама программа Claude Code автоматически запускает на событие (до или после вызова инструмента).
- **Ворота (gate)** — место, где процесс останавливается и ждёт явного «да» от человека.
- **Worktree** — отдельная рабочая копия git-репозитория. Позволяет нескольким агентам править код параллельно и не мешать друг другу.

---

## 1. Общая схема

ECC — это не «операционная система», а **набор текстовых инструкций плюс несколько скриптов на Node.js**. Постоянно работающего процесса-диспетчера в нём нет. «Ядром» служит файл `CLAUDE.md`/`AGENTS.md`: модель читает его в начале сессии и по таблицам решает, кому что поручить. Специалисты — это 71 файл в `agents/`. Каждый из них — роль с узким набором инструментов (у `planner` есть только Read/Grep/Glob, то есть он ничего не может изменить). Память — обычные файлы: markdown и JSON в `data/` или `.claude/plans/`, никаких баз данных. Расписание в ECC своего нет. Проект прямо говорит, что нужен внешний планировщик (cron, systemd, GitHub Actions), который запускает `claude -p "..."`. Проверки бывают трёх видов: ворота с человеком (одобрить план, подтвердить коммит), независимые ревьюеры (santa-loop, orch-review) и тесты. Почти всё, что связано с параллельностью (tmux, worktree, DevFleet, Codex CLI), рассчитано на **локальный компьютер разработчика**.

```
                ┌───────────────────────────────────────────┐
  ЧЕЛОВЕК ───►  │ ЯДРО: CLAUDE.md / AGENTS.md               │
   (ворота)     │ таблица «ситуация → агент», принципы,     │
     ▲          │ contexts/{dev,research,review}.md = режимы│
     │          └──────────────┬────────────────────────────┘
     │                         │ маршрутизация словами, не кодом
     │          ┌──────────────▼────────────────────────────┐
     │          │ КОНВЕЙЕРЫ (навыки): orch-pipeline,         │
     │          │ plan-orchestrate, team-*, council          │
     │          └──┬───────────┬──────────────┬─────────────┘
     │             │           │              │
     │     ┌───────▼───┐ ┌─────▼──────┐ ┌─────▼─────────────┐
     │     │СПЕЦИАЛИСТЫ│ │ПАРАЛЛЕЛЬНО │ │ ВНЕШНИЕ МОДЕЛИ     │
     │     │agents/*.md│ │tmux+worktree│ │ multi-* (Codex),   │
     │     │(субагенты)│ │DevFleet(MCP)│ │ council-multi-model│
     │     └───────┬───┘ └─────┬──────┘ └─────┬─────────────┘
     │             └───────────┼──────────────┘
     │                         ▼ артефакты-передачи
     │          ┌───────────────────────────────────────────┐
     │          │ ПАМЯТЬ = файлы: task_list, .claude/plans/*,│
     │          │ task.md / handoff.md / status.md, data/*   │
     │          └──────────────┬────────────────────────────┘
     │                         ▼
     │          ┌───────────────────────────────────────────┐
     └───────── │ ПРОВЕРКИ: Gate 1 (план), Gate 2 (коммит),  │
                │ santa-loop (2 ревьюера), orch-review       │
                │ (fail-closed), тесты, loop-operator        │
                └───────────────────────────────────────────┘
  РАСПИСАНИЕ: не входит в ECC → внешний cron/CI запускает `claude -p`
```

Один принцип проходит через весь проект: **передача между шагами идёт через видимые файлы, а не через «память» модели**. В `skills/orch-pipeline/SKILL.md` он сформулирован так:

> The pipeline carries no hidden state — the planning docs *are* the handoff

## 2. Механики по отдельности

### 2.1. Ядро: agentic-os, AGENTS.md, SOUL.md, agent.yaml, contexts

**Что это.** Описание, как превратить один проект Claude Code в постоянную систему с ролями, командами, памятью и расписанием.

**Как устроено** (`skills/agentic-os/SKILL.md`):
- `CLAUDE.md` — «ядро», которое играет роль COO (операционного директора). Внутри таблица агентов с колонкой Trigger (по каким словам вызывать) и пять правил маршрутизации: разобрать запрос → найти совпадение в таблице → загрузить `agents/<name>.md` → передать задачу → свести результат.
- У каждого агента есть раздел **Memory Scope**: какие файлы он читает и куда дописывает лог.
- Память лежит в `data/`: `daily-logs/` (только дописывание), `decisions/` (решения в формате ADR, Architecture Decision Record — короткая запись «что решили и почему»), `inbox/`, `projects/`.
- В конце каждой сессии пишется рефлексия «что сработало / что нет / что поменять».
- Ограничения размера: ядро меньше 200 строк, файл агента меньше 100.

> The kernel should be **small and declarative**. Routing logic lives in plain markdown tables, not code.
> — `skills/agentic-os/SKILL.md`

> Never rename existing fields. Add new fields and mark old ones deprecated
> — там же (правило эволюции схемы данных)

`AGENTS.md` — настоящее ядро самого ECC: таблица из 71 агента и список «Use agents proactively without user prompt» (сложная фича → planner, написан код → code-reviewer и т.д.). `SOUL.md` — пять принципов «личности» (Agent-First, Plan Before Execute…). `agent.yaml` — машиночитаемый «паспорт»: предпочитаемая модель, запасная модель, перечень навыков и команд (формат gitagent, нужен для переноса на другие оболочки). `contexts/*.md` — три коротких «режима» (dev / research / review), у каждого свои приоритеты и предпочтительные инструменты.

**Сильное.** Маршрутизация лежит в таблице, и её может прочитать и поправить не программист. Память без инфраструктуры. Есть правило не переименовывать поля. Рефлексия даёт обучение без правки кода.

**Слабое.** Расписание в agentic-os — это LaunchAgent, systemd и pm2, то есть только локальный компьютер. Строку `claude --cwd ... --command /daily-sync` из примеров стоит считать неточной. В соседнем навыке `autonomous-agent-harness` используется корректная форма `cd "/path" && claude -p "..."`. Утверждение, что встроенный cron Claude Code «умирает вместе с сессией», к облачным запланированным задачам не относится: они хранятся на сервере.

### 2.2. Конвейер с воротами: orch-pipeline и пять обёрток, /plan, planner

**Что это.** Единый движок «исследовать → спланировать → сделать через тесты → проверить → закоммитить» и пять тонких обёрток под разные типы работы.

**Как устроено** (`skills/orch-pipeline/SKILL.md`):
1. **Шаг 0 — оценка размера.** Задача получает уровень trivial / small / standard / large по трём сигналам: сколько файлов затронуто, появляется ли новая зависимость, насколько неоднозначен дизайн. Берётся **максимальный** уровень из трёх. Уровень объявляется одной строкой, чтобы человек мог его оспорить. От уровня зависит, какие фазы вообще запускаются: trivial идёт сразу в 4 → 5 → 6.
2. Фазы: 0 Intake → 1 Research → 2 Plan (агент `planner`, на выходе `task_list`) → **GATE 1** → 3 Scaffold (только для MVP) → 4 Implement (TDD) → 5 Review (+ `security-reviewer`, если затронуты авторизация, ввод пользователя, SQL, файлы, внешние API, криптография или секреты) → 6 Commit → **GATE 2**.
3. Обёртки различаются **первым ходом**:
   - `orch-add-feature` — новые падающие тесты;
   - `orch-fix-defect` — сначала воспроизвести баг падающим тестом;
   - `orch-change-feature` — сначала переписать *существующие* тесты под новое поведение;
   - `orch-refine-code` — убедиться, что тесты зелёные, и ничего нового не добавлять;
   - `orch-build-mvp` — прочитать спецификацию и нарезать её на вертикальные срезы.

> This family is **gated, not autonomous** … Everything between the gates flows without stopping.
> — `skills/orch-pipeline/SKILL.md`

> Proving the bug exists first is what separates a fix from a tweak.
> — `skills/orch-fix-defect/SKILL.md`

`/plan` (`commands/plan.md`) — то же планирование, но в одной сессии. Сначала он ищет в коде образцы, которым надо следовать («Patterns to Mirror»: именование, обработка ошибок, тесты), затем показывает план и ждёт «yes / modify». Агент `agents/planner.md` задаёт формат плана: шаг → файл → почему → зависимости → риск. Главное правило: «Each phase should be mergeable independently», то есть каждая фаза должна приносить пользу сама по себе.

**Сильное.** Объём церемоний соразмерен риску. Ворот ровно два, и стоят они там, где ошибка дороже всего: до начала работы и до необратимого шага. Планировщик физически не может писать файлы. Тип задачи (новое / поломка / изменение / рефакторинг) определяет первый шаг.

**Слабое.** Всё заточено под код (TDD, conventional commits, покрытие 80%). Обёртки — только текст, и соблюдение ворот держится на дисциплине модели, а не на механизме.

### 2.3. План → готовые команды: plan-orchestrate

**Что это.** Маршрутизатор. Читает документ-план, делит его на шаги, относит каждый шаг к категории и **выдаёт готовую команду для вставки**. Сам ничего не запускает.

**Как устроено.** У каждой категории (fix, impl, refactor, docs…) есть своя команда. Конфликты разрешаются таблицей приоритетов и явными исключениями. Например, «Build a new API» — это создание нового, а не починка сборки. Ключевое правило — **fail closed** («при сомнении — закрыто»): если команда не умеет принять описание шага как аргумент, шаг помечается `BLOCKED`, а не выдаётся «голой» командой. Каждое описание задачи начинается с метки-ссылки на план, содержит 1–3 критерия приёмки и укладывается в 200–600 символов. Текст плана считается недоверенным: если в нём просят доступ к секретам или удаление, шаг блокируется.

> Start with `[Plan: <path>#step-<id>]` — this marker is the step's machine-readable link.
> — `skills/plan-orchestrate/SKILL.md`

**Сильное.** У каждой порученной задачи есть обратная ссылка на шаг плана и проверяемые критерии. Таблица команд сверяется тестом (`tests/skills/plan-orchestrate-registry.test.js`), так что документация не «уплывает».

**Слабое.** Человеку приходится вставлять команды вручную. Классификация по ключевым словам хрупкая. Попутное наблюдение: в `docs/COMMAND-AGENT-MAP.md` до сих пор значится `/orchestrate`, хотя это уже устаревшая прослойка (`legacy-command-shims/`). Рассинхрон документации встречается даже здесь.

### 2.4. Команда агентов: team-agent-orchestration и team-builder

**`team-agent-orchestration`** — управление агентами как командой людей. Каждая задача оформляется **карточкой**: owner (кто отвечает), scope (что можно трогать), state, acceptance (критерии приёмки), merge_gate (точное условие вливания), handoff (ссылка на отчёт). Состояний семь: Backlog → Ready → Running → Review → Blocked → Merged → Archived, и у каждого записан критерий выхода. Нужна «панель управления»: владелец, ветка, **последний heartbeat** (сигнал «я жив»), блокеры с указанием, кто их снимает.

> Do not add more automation until the operator can answer: who owns this, what changed, what gate failed, and what can safely merge?

Описаны типовые сбои. «Agent soup» — агентов много, а владельца нет. «Board theater» — доска есть, а критериев приёмки на карточках нет. «Invisible work» — результат остался только в переписке.

**`team-builder`** — интерактивное меню. Находит доступных агентов, группирует их по доменам, даёт выбрать **не больше 5** и запускает их **параллельно на одну задачу** без общения между собой. Затем сводит ответы в отчёт: где согласны, где конфликт, что делать дальше. Если агент упал, это отмечается в отчёте, а не скрывается.

**Сильное.** Карточка — лучший переносимый артефакт во всём блоке. Ограничение на 5 агентов объяснено расходом токенов и убывающей отдачей.

**Слабое.** Самой доски в ECC нет, только требования к ней. team-builder вызывает `claude agents` и читает `~/.claude/agents`, то есть рассчитан на локальную установку.

### 2.5. Параллельные исполнители: claude-devfleet, dmux-workflows, LANE-RULES

**claude-devfleet** — внешний сервер (не входит в ECC), подключается по MCP на `localhost:18801`. Работа идёт по схеме `plan_project` → **граф миссий** с `depends_on` (зависимостями) → показать план человеку → запустить корневую миссию → остальные стартуют сами, когда готовы зависимости (`auto_dispatch=true`). Одновременно работают не больше 3 агентов, каждый в своём worktree. После завершения миссии выполняется авто-слияние, а `get_report` возвращает структурированный отчёт: files_changed, what_done, errors, next_steps.

**dmux-workflows** — несколько агентов в панелях tmux плюс worktree. Полезная часть здесь — паттерны: «исследование ∥ реализация», «одна папка — три ревьюера с разными фокусами», «смотритель тестов + исправитель». Хелпер `scripts/orchestrate-worktrees.js` на каждого исполнителя создаёт ветку, worktree и три файла в `.orchestration/<session>/<worker>/`:

```
task.md     — задача, ветка, пути; «Do not spawn subagents… Report results in your final response.»
handoff.md  — шаблон: Summary / Files Changed / Tests / Verification / Follow-ups
status.md   — State: running|failed|…, Updated, Branch
```
(шаблоны в `scripts/lib/tmux-worktree-orchestrator.js`, запуск исполнителя в `scripts/orchestrate-codex-worker.sh`)

**docs/LANE-RULES.md** — правила для «полосы», то есть одного ограниченного исполнителя. Пожалуй, самый честный и полезный текст блока: видно, что его написали после реальных сбоев.

> You are one bounded worker. One task, one branch, one PR or one receipt, then stop.
> … No receipts about receipts, no independent review of your own output … Your final message is the receipt (under 300 words …)
> If blocked … stop and say exactly what is needed. Do not wait, poll, or sleep. … Do not spawn subagents.

**Сильное.** Изоляция исполнителей. Явный отчёт по шаблону. Запрет рекурсии (исполнитель не плодит своих агентов). Запрет внешних действий: не сливать в main, не публиковать, не отправлять письма.

**Слабое.** tmux, worktree, localhost-MCP, пути `~/GitHub/...` и «mini» — всё это локальное железо автора. В облачной сессии без подключённого компьютера dmux и DevFleet не заработают. Переносятся только паттерны и шаблоны файлов.

### 2.6. Несколько моделей: /multi-plan, /multi-workflow, /multi-execute

**Как устроено.** Claude — оркестратор и **единственный, кто пишет файлы** («Code Sovereignty»). Codex отвечает за бэкенд, Antigravity за фронтенд. Обоим даётся *исходное* требование без чужих мнений, затем Claude ищет консенсус и расхождения. `/multi-plan` сохраняет план в `.claude/plan/<feature>.md` и **обязан остановиться**: исполнение запускается отдельной командой в новой сессии. В `/multi-workflow` перед стартом требования оцениваются по шкале 0–10, и при оценке ниже 7 работа останавливается с уточняющими вопросами. В `/multi-execute` ответ внешних моделей считается «грязным прототипом» (unified diff), который Claude обязан переписать.

> External models have **zero filesystem write access**, all modifications by Claude
> — `commands/multi-plan.md`

**Слабое.** Нужен внешний рантайм `ccg-workflow` (`~/.claude/bin/codeagent-wrapper`), а также установленные CLI и ключи. В облаке без настройки контейнера это не работает. Идея одного писателя и оценки готовности требований переносится полностью.

### 2.7. Автономность и расписание: autonomous-agent-harness, /loop-start, /loop-status, loop-operator, /checkpoint

**autonomous-agent-harness** — честный, после правок, рецепт «вечного агента». Внутри: память (встроенная `~/.claude/projects/*/memory/` плюс необязательный MCP-граф знаний), очередь задач в файле `task-queue.md` (Active / Completed), `/loop 30m ...` внутри сессии, внешний планировщик для всего остального. Первым идёт раздел о согласии: ничего не планировать, не публиковать и не трогать чужие ресурсы без явного разрешения на конкретную возможность.

> This is a setup pattern, not a bundled always-on runtime.
> — `skills/autonomous-agent-harness/SKILL.md`

**/loop-start** готовит цикл одного из четырёх видов (sequential, continuous-pr, rfc-dag, infinite) в режиме safe или fast, пишет инструкцию запуска (runbook) в `.claude/plans/` и требует **явное условие остановки**. Агент **loop-operator** задаёт правила эскалации:

> no progress across two consecutive checkpoints · repeated failures with identical stack traces · cost drift outside budget window
> — `agents/loop-operator.md`

**/loop-status** через CLI `ecc loop-status` сканирует **локальные** журналы сессий в `~/.claude/projects/**` и ищет «зависшие» вызовы инструментов. **/checkpoint** работает так: проверка → git stash или коммит с именем → строка в `.claude/checkpoints.log` → позже сравнение «было/стало» по файлам, тестам и покрытию.

**Слабое.** /loop-status и /checkpoint завязаны на локальные файлы и git. Сами правила эскалации и требование условия остановки переносятся куда угодно.

### 2.8. Проверки: /santa-loop и workflows/orch-review

**/santa-loop** (поверх навыка `santa-method`). Два независимых ревьюера (Claude Opus и, по возможности, модель другого поставщика) получают **одну и ту же рубрику**, где у каждого критерия есть объективное PASS/FAIL. Оба PASS — «NICE», выпускаем. Хотя бы один FAIL — «NAUGHTY»: исправляем *только* отмеченное и запускаем **свежих** ревьюеров без памяти о прошлом раунде. Не больше 3 раундов, затем эскалация к человеку.

> A failed external invocation is not an approval and must not silently become a fallback
> — `commands/santa-loop.md`

**workflows/orch-review.workflow.js** — единственный настоящий программный оркестратор в блоке, скрипт для встроенного инструмента Workflow. Устроен так:
1. Ревьюеры по измерениям работают параллельно: качество — всегда, язык — по ситуации, безопасность — по регулярному выражению-триггеру.
2. Ответы обязаны соответствовать JSON-схеме. Находка уровня HIGH или CRITICAL без поля `proof` не пройдёт **на уровне схемы**.
3. Дубликаты убираются по фрагменту кода (в тестах 11 находок свелись к 4).
4. Каждую серьёзную находку проверяет отдельный «скептик». Снять блокер он может только при уверенности ≥ 0.8.

> Uncertainty must never clear a blocker.
> — `workflows/orch-review.workflow.js`

Важная деталь архитектуры:

> native workflows run autonomously in the background and cannot pause for interactive approval
> — `workflows/README.md`

Поэтому ворота с человеком остаются в основном диалоге, а скрипт обслуживает только автономный участок *между* воротами.

**Сильное.** Подход «при сбое — закрыто» (fail closed) соблюдается везде: упал ревьюер — вердикт не может быть APPROVE. Строгость задаётся схемой, а не просьбой в промпте.

**Слабое.** Всё это про проверку кода. Pilot-статус. Инструмент Workflow должен быть доступен в оболочке.

### 2.9. Самоулучшение: harness-optimizer

Агент улучшает **настройки системы** (хуки, маршрутизацию, контекст), а не продукт. Порядок работы: снимок «до» → минимальное обратимое изменение → прогон оценок (evals) → при провале **автоматический откат к снимку**. Метрики: pass@3 (хотя бы 1 из 3 прогонов прошёл) для новых способностей и pass^3 (все 3 прошли) для критичных регрессий. Любое изменение, касающееся безопасности или прав, блокируется до одобрения человеком.

**Переносимая идея:** любая правка инструкций агентам проверяется на фиксированном наборе тестовых заданий до и после.

### 2.10. Мелочи: /aside

`/aside <вопрос>` — побочный вопрос посреди задачи. Только чтение, без правок. Ответ оформляется как `ASIDE: … — Back to task: …`. Если вопрос на деле меняет направление работы, нужно переспросить, а не молча свернуть. Работает в любой среде.

## 3. Council: «четыре голоса» подробно

Файлы: `skills/council/SKILL.md`, `skills/council-multi-model/SKILL.md` и `scripts/review-with-codex.js`.

**Назначение.** Только решения в условиях неопределённости: «есть несколько достойных путей и нет очевидного победителя». Не ревью кода, не планирование и не архитектура. Для них есть santa-method, planner и architect, о чём прямо сказано в таблице «When NOT to Use».

### Роли

| Голос | Через какую линзу смотрит | Кто это технически |
|---|---|---|
| Architect | правильность, поддерживаемость, долгосрочные последствия | **сам ведущий Claude**, в текущем контексте |
| Skeptic | оспаривает саму постановку вопроса, ищет простейшую альтернативу | свежий субагент |
| Pragmatist | скорость выпуска, влияние на пользователя, реальная эксплуатация | свежий субагент |
| Critic | крайние случаи, риски, сценарии провала | свежий субагент |

### Протокол (6 шагов)

1. **Выделить настоящий вопрос**: что решаем, какие ограничения, что считать успехом. Если вопрос расплывчатый — один уточняющий вопрос человеку.
2. **Собрать минимум контекста**: только то, что меняет ответ.
3. **Architect высказывается первым и письменно**, *до* чтения остальных: позиция, три сильнейших довода, главный риск своего пути. Это защита от того, чтобы итог просто повторял чужие голоса.
4. **Три голоса запускаются параллельно** и получают **только вопрос и сжатый контекст, без истории разговора**. Это главный механизм против «якорения» (anchoring, когда первое услышанное мнение тянет за собой всё обсуждение):
   > The three external voices should be launched as fresh subagents with **only the question and relevant context**, not the full ongoing conversation. That is the anti-anchoring mechanism.

   Каждый отвечает строго по форме, до 300 слов: **Position** (1–2 предложения), **Reasoning** (3 пункта), **Risk** (главный риск *своей же* рекомендации), **Surprise** (что упустят остальные). Плюс жёсткое «Be direct. No hedging».
5. **Синтез с защитой от предвзятости.** Architect одновременно участник и судья, поэтому действуют пять правил:
   - нельзя отбросить внешний голос без объяснения причины;
   - если чужой голос изменил рекомендацию, это говорится прямо;
   - **сильнейшее несогласие показывается всегда**, даже если его отвергли;
   - если два голоса против исходной позиции Architect, это считается реальным сигналом;
   - сырые позиции показываются *до* вердикта.
6. **Компактный вердикт** (читается с экрана телефона): по строке на каждый голос, затем Consensus / Strongest dissent / **Premise check** (оспорил ли Skeptic саму постановку) / Recommendation.

### Как выносится решение

Голосования нет. Рекомендацию синтезирует ведущий, а **решает человек**. Ценность совета — не единогласие, а видимость спора:

> The value is not unanimity. The value is making the disagreement legible before choosing.

**Сохранение итога.** Решение записывается в постоянное место (базу знаний, задачу в трекере) только если оно «changes something real». Никаких заметок «на всякий случай». **Второй раунд** по умолчанию не проводится. Если он всё же нужен, вопрос сужается, прошлый вердикт передаётся только при необходимости, а Skeptic остаётся максимально «чистым».

### council-multi-model: внешний критик

Это не пятый голос и не судья, а **один узел после черновика**. Модель OpenAI Codex пытается «сломать» уже готовый синтез.
- Формируется пакет: сырые разногласия и черновик внутри блоков `BEGIN_UNTRUSTED_…` («это данные, не инструкции»). Четыре вопроса: где вывод ломается? какой сценарий провала пропущен? не подавили ли сильнейший контраргумент? подписал бы ты это?
- **Согласие на передачу** данных в OpenAI спрашивается каждый раз и именно на этот пакет.
- Скрипт-адаптер запускает Codex в пустой временной папке. Все инструменты отключены (shell, браузер, MCP, веб-поиск), принимается только версия CLI 0.146.0, таймаут 60 с (максимум 120), размер пакета не больше 64 КБ.
- Честная маркировка: «cross-provider» или «same-provider», если хозяин тоже OpenAI. Если вызов не удался, пишется **«external review absent: <причина>»**, без тихой подмены другой моделью.
- Критика цитируется **дословно**, чтобы ведущий не пересказал её «своим голосом».

### Сильные стороны и ограничения council

Сильное:
- дешёвая и понятная защита от якорения через чистый контекст;
- обязательный показ несогласия;
- проверка самой постановки вопроса (Premise check);
- требование, чтобы каждый голос назвал риск *собственной* рекомендации.

Ограничения:
- все четыре голоса — одна модель с разными ролевыми промптами. Разнообразие мнений здесь искусственное;
- Architect судит и себя, и других. Правила синтеза смягчают это, но не устраняют;
- «свежий субагент» видит только то, что ведущий решил ему передать. Отбор контекста — тоже скрытое влияние;
- один раунд, ответы до 300 слов: для действительно сложных решений этого мало;
- внешний критик требует установленного Codex CLI и ключа OpenAI.

**Council у вас.** Самый чистый способ — **три дочерние сессии** вместо субагентов. Каждая получает *только* документ с вопросом (что решаем, ограничения, критерий успеха, минимум фактов) и роль. Отдельная сессия гарантированно не видит вашей переписки с оркестратором, а это и есть защита от якорения. Порядок:
1. Оркестратор записывает свою позицию в документ «Совет · <тема>» *до* запуска голосов.
2. Запускает Скептика, Прагматика и Критика с шаблоном ответа «Позиция / 3 довода / Риск / Что упустят другие».
3. Каждый голос последним действием дописывает свой ответ в документ или отправляет сообщение оркестратору.
4. Оркестратор пишет вердикт по формату: консенсус, сильнейшее несогласие, проверка постановки, рекомендация.
5. Решаете вы. В журнал «Решения» запись попадает, только если что-то реально меняется.

Подходящие вопросы: брать ли клиента на невыгодных условиях, менять ли регламент спринтов, нанимать или автоматизировать. Внешнего критика (Codex) можно пропустить. Если хочется «другого взгляда», используйте другую модель Claude, но честно помечайте это как «тот же поставщик».
